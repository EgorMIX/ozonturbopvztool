# Известные проблемы (на момент импорта, v1.4.0)

Всё ниже найдено **чтением кода**; в живом Chrome это не воспроизводилось (в среде, где собирался
репозиторий, браузера нет). Поэтому в каждом пункте есть «как проверить» — для владельца проекта.
Номера строк — на момент импорта; в коде ищи по имени функции.

Порядок исправления: сначала P0 (надёжность главной функции — уведомлений), потом P1 (авто-пакеты), P2 по желанию.
После каждой правки — `npm run check`.

## P0 — надёжность уведомлений

### 1. Service worker не дожидается загрузки состояния — ИСПРАВЛЕНО (ждёт проверки в Chrome)
- **Что сделано:** загрузка из storage — промис `ready` (`applyLoadedState`, низ `background.js`); `onAlarm` и
  `onButtonClicked` начинаются с `await ready`, `onMessage` → `ready.then(() => handleMessage(...))`, `return true`.
  Журнал `eventLog` по-прежнему только в памяти SW (после перезапуска SW он пуст — это ожидаемо).
- Ниже — исходное описание проблемы.
- **Где:** `background.js` — `chrome.storage.local.get([...])` внизу файла (≈521–548) заполняет `timerState`, `settings`,
  `modeState` **асинхронно**, а обработчики `chrome.alarms.onAlarm` (≈198) и `chrome.runtime.onMessage` (≈344)
  регистрируются сразу и срабатывают при пробуждении SW, не дожидаясь этой загрузки.
- **Что происходит:** MV3-SW засыпает примерно через 30 с без событий. Пока открыта активная вкладка Ozon,
  `content.js` шлёт `TIMER_FOUND` каждые 10 с и SW живёт. Но если вкладка закрыта или «заморожена» Chrome,
  SW будит именно аларм `threshold_*` — и обработчик видит дефолтное `timerState.seconds === null`
  (≈215–219) и **молча ничего не делает**: уведомление теряется. Та же гонка с первым `TIMER_FOUND` после
  перезапуска SW: `prev === null` → «новый таймер» → повторное «Приёмка начата» и сброс `firedFor`
  (повторные пороги); потом запоздавший `storage.get` затирает свежее состояние старым (≈535).
  Заодно `badge_tick` после пробуждения может стереть бейдж (`updateBadge(null)`, ≈208) до следующего тика.
- **Исправление:** `const ready = chrome.storage.local.get([...]).then(applyLoaded);` и в каждом обработчике
  начинать с `await ready` (для `onMessage`: `ready.then(() => handle(msg, sendResponse)); return true;`).
  Журнал `eventLog` живёт только в памяти SW — при желании хранить в `chrome.storage.session`.
- **Как проверить:** `chrome://extensions` → у расширения «Service worker» → DevTools → остановить SW;
  в popup → «Отладка» → симуляция таймера на ~6 мин; закрыть вкладку Ozon; дождаться порога — уведомление должно прийти.

### 2. Модуль прокси ломает сеть браузера — ИСПРАВЛЕНО (ждёт проверки в Chrome)
- **Что сделано (владелец выбрал «чинить»):**
  1. `clearProxy()` больше не ставит `mode: 'direct'`, а делает `chrome.proxy.settings.clear()` и только если настройкой
     управляет это расширение (`levelOfControl === 'controlled_by_this_extension'`). Чужой прокси / VPN не трогается;
     оставшийся от старой версии `direct` снимается при первом старте SW.
  2. Прокси ставится PAC-скриптом (`mode: 'pac_script'`): через него идёт только `PROXY_HOSTS` (`api.telegram.org`),
     всё остальное — `DIRECT`. Хост/порт проверяются `validateProxy()` до подстановки в PAC.
  3. Логин/пароль HTTP-прокси отдаются из `chrome.webRequest.onAuthRequired` (`asyncBlocking`, разрешения `webRequest` +
     `webRequestAuthProvider`); повторный запрос на тот же `requestId` = неверный пароль → отмена. SOCKS5 с логином
     Chrome не поддерживает — `validateProxy()` отказывает с понятной причиной.
  4. Если прокси браузера занят другим расширением или политикой — не применяем и сообщаем это в «Тест прокси».
     У теста таймаут 15 с и расшифровка типичных ошибок.
- **Остаточные ограничения Chrome:** пока наш прокси включён, системный прокси / VPN-расширение для остальных сайтов
  не действуют (настройка прокси в браузере одна); MTProto-прокси через `fetch` невозможен. Это написано в popup.
- Ниже — исходное описание.
- **Где:** `background.js` `applyProxy()` (≈121–138), вызывается на **каждом** старте SW (≈538) и при `SETTINGS_UPDATED`.
- **Что происходит:**
  1. Если прокси выключен, код всё равно делает `chrome.proxy.settings.set({ mode: 'direct' })` — это перетирает
     системный прокси / настройки VPN-расширений пользователя. Само наличие разрешения `proxy` + этот вызов
     на старте — главный риск.
  2. Если включён: `proxyForHttps` действует на **весь** HTTPS браузера (включая сам Ozon), а не только на Telegram.
  3. `username`/`password` сохраняются, но нигде не используются (нужен `webRequest.onAuthRequired`, а SOCKS5 с
     логином Chrome вообще не поддерживает).
  4. В UI только SOCKS5 и HTTP; MTProto через `fetch` невозможен.
- **Что делать (выбери вместе с владельцем):**
  - срочный минимум: не вызывать `proxy.settings.set` при выключенном прокси; при переходе включён→выключен делать
    `chrome.proxy.settings.clear({ scope: 'regular' })` один раз;
  - правильнее: убрать модуль и разрешение `proxy` совсем, а Telegram доставлять через сервер-таймер
    (см. `docs/backend-idea.md`) или положиться на ntfy.
- **Как проверить:** `chrome://net-internals/#proxy` / «Настройки → Система → прокси» до и после перезапуска расширения.

### 3. Повторные уведомления порогов — ИСПРАВЛЕНО (ждёт проверки в Chrome)
- **Что сделано:** `SETTINGS_UPDATED` и `setMode('active')` не обнуляют `firedFor`, только пересоздают алармы ещё не
  сработавших порогов; «Сохранить» на вкладке «Пакеты» не шлёт `SETTINGS_UPDATED`; кратковременный `TIMER_LOST` не
  сбрасывает приёмку (п. 4).
- Ниже — исходное описание.
- **Где:** `background.js`: `SETTINGS_UPDATED` (≈402–423, строка `timerState.firedFor = []` ≈419),
  `TIMER_LOST` (≈382–392), `setMode('active')` (≈84).
- **Что происходит:** после сброса `firedFor` вызывается `scheduleThresholdAlarms()`, который **сразу** шлёт
  все уже пройденные пороги (≈235–237). `popup.js` отправляет `SETTINGS_UPDATED` из трёх мест
  (`saveBtn` ≈299, `saveBagsBtn` ≈525, `saveBagsLimitBtn` ≈561) — то есть нажатие «Сохранить» **на вкладке «Пакеты»**
  при таймере меньше 30 минут пришлёт повторные 30/15-минутные уведомления во все каналы.
  Так же срабатывает кратковременное исчезновение элемента таймера на странице (ререндер): `TIMER_LOST` →
  таймер снова найден → пороги заново.
- **Исправление:** хранить `firedFor` привязанным к сессии приёмки (см. п. 4); `SETTINGS_UPDATED` не обнуляет
  `firedFor`, а только пересоздаёт алармы для ещё не сработавших порогов; вкладка «Пакеты» не должна слать
  `SETTINGS_UPDATED` вовсе (`bags-content.js` сам читает storage через `onChanged`).
- **Как проверить:** симулировать таймер на 12 минут (Отладка), дождаться/пропустить 15-минутный порог, нажать
  «Сохранить» — повторных уведомлений быть не должно.

### 4. Нет понятия «сессия приёмки»; флаг `startNotified` — ИСПРАВЛЕНО (ждёт проверки в Chrome)
- **Что сделано:** в `timerState` добавлены `endsAt` и `lostAt`. Та же приёмка — если `endsAt` совпадает в пределах
  ±90 с (`SESSION_TOLERANCE_MS`), иначе новая: сброс `firedFor` и `startNotified`, новые алармы. `TIMER_LOST` ставит
  `lostAt` и аларм `timer_lost_grace` на 2 мин (`LOST_GRACE_MIN`); если таймер не вернулся — `endSession()`. Если время
  уже вышло — сессия завершается сразу. Состояние без `endsAt` (от старой версии) пересчитывается из `seconds/updatedAt`.
- Ниже — исходное описание.
- **Где:** `background.js`, `TIMER_FOUND` (≈346–370).
- **Что происходит:** новая сессия определяется как «значение выросло больше чем на 60 с относительно последнего
  присланного» (`isNewSession`, ≈350). После `TIMER_LOST` `seconds === null`, поэтому следующий таймер считается
  `isReallyNew`, но `startNotified` **не сбрасывается** — уведомления «Приёмка начата» для следующей приёмки не будет.
  С другой стороны, при рестарте SW (п. 1) оно может прийти повторно.
- **Исправление (предложение):** идентифицировать сессию абсолютным временем окончания
  `endsAt = Date.now() + seconds * 1000`. Новое чтение — та же сессия, если `|endsAt_new − endsAt_old| ≤ ~90 с`,
  иначе новая (сбросить `firedFor` и `startNotified`, пересоздать алармы). `TIMER_LOST` не должен сразу стирать
  сессию — только если таймер не виден заметно дольше обычного ререндера или `endsAt` уже в прошлом.
  Хранить `endsAt` в `timerState`. Это же ровно то, что нужно серверу-таймеру (`docs/backend-idea.md`).
- **Как проверить:** две приёмки подряд (или симуляция дважды) — «Приёмка начата» должно прийти оба раза и только по разу.

## P1 — модуль «Авто-пакеты» (`bags-content.js`, вкладка «Пакеты» в popup)

### 5. Лимиты и счётчики — ИСПРАВЛЕНО a–e (ждёт проверки в Chrome); вопрос владельцу ниже открыт
- **Что сделано:** клики ограничены остатком лимита; одна серия за раз (`inFlight`, повтор после серии, если DOM
  менялся); перед каждым кликом проверяются input, кнопка и лимит; `bagsSessionStats` слушается в `onChanged`;
  статистика пишется один раз в конце серии «прочитать → прибавить → записать»; сброс статистики или изменение лимита
  снова запускает наблюдатель.
- Ниже — исходное описание.
- **a) Перебор лимита.** `tryFill()` (≈182–221) считает `clicks = available - current` и не учитывает остаток квоты:
  лимит M=1 при «доступно 2» даст 2 клика (в статистике 2/1). Исправление:
  `clicks = Math.min(available - current, quota > 0 ? quota - sessionStats[label] : Infinity)`.
- **b) Сброс статистики не доходит до вкладки.** Кнопка «Сбросить» (`popup.js` ≈608) пишет нули в storage, но
  `bags-content.js` держит свой `sessionStats` в памяти и не слушает `changes.bagsSessionStats`; следующий клик
  перезапишет storage старым значением +1, а квота считается по устаревшему числу. То же при нескольких
  вкладках Ozon (каждая перезаписывает чужое). Исправление: подписаться на `bagsSessionStats` в `onChanged`
  и обновлять локальную копию; инкремент делать «прочитать → прибавить → записать».
- **c) Повторный запуск во время серии кликов.** `MutationObserver` (дебаунс 200 мс) может запустить второй
  `tryFill()`, пока первая серия (шаг 150 мс) ещё кликает: `current` читается «на полпути» и планируются лишние клики.
  Спасает только то, что Ozon отключает «+» на максимуме; с квотой возможен перебор. Исправление: флаг `inFlight`
  на время серии и проверка актуального значения input непосредственно перед каждым кликом.
- **d) Не перезапускается после достижения лимитов.** `stopObserving()` (≈215) отключает наблюдатель; повышение лимита
  или сброс статистики его не включают (в `onChanged`, ≈43–49, перезапуск только при смене `enabled`/`sizes`) —
  до перехода на другую страницу. Исправление: перезапускать `init()` и при смене квоты/статистики.
- **e)** `saveStats()` пишет в storage на каждый клик — достаточно раз в конце серии.
- **Вопрос владельцу:** счётчик называется `sessionStats`, но по факту он накопительный до ручного сброса и не
  привязан к экрану выдачи. Нужен ли лимит «на один заказ/экран выдачи» (сбрасывать при смене
  `/orders/session-new/<id>`)? Сейчас этого нет.

### 6. Ошибки `popup.js` — ИСПРАВЛЕНО
- **Что сделано:** первый обработчик `#bagsEnabled` (с `#bagsStatus`) удалён; переключатель применяется кнопкой
  «Сохранить»; ключи убраны из `scripts/known-issues.json`.
- Ниже — исходное описание.
- Два обработчика `change` на `#bagsEnabled`: `popup.js` ≈480–489 и ≈517–519.
- Первый после записи в storage обращается к `#bagsStatus`, которого в `popup.html` больше нет, → `TypeError`

- **Исправление:** удалить первый блок (≈480–489), оставить второй; убрать обе строки из `scripts/known-issues.json`.
  Если нужно «применять сразу» — оставить запись в storage, но без `#bagsStatus`.

## Аудит после v1.4 (ошибки и уязвимости) — ИСПРАВЛЕНО, ждёт проверки в Chrome

- **«Сбросить» ручного таймера** слал `TIMER_LOST`, который после п. 4 ждёт 2 мин. Теперь `TIMER_CLEAR` → `endSession()`.
- **Тесты Telegram / ntfy / прокси подменяли рабочие `settings`** (во время теста порог уходил в выключенный Telegram,
  несохранённый токен оставался действующим, «Сохранить» во время теста прокси откатывался). Теперь тестовые данные
  передаются параметром (`sendTelegram(…, tgCfg)`, `sendNtfy(…, nCfg)`), для прокси — `proxyTestOverride`.
- **Отправитель сообщений не проверялся.** `isAllowedSender()`: от вкладок — только `TIMER_FOUND`/`TIMER_LOST` и только с
  `https://turbo-pvz.ozon.ru/`, остальное — только со страниц расширения. `TIMER_FOUND.seconds` проверяется (0…86400).
- **`timerState.url` открывался без проверки** — теперь только `https://turbo-pvz.ozon.ru/…` (`openTimerPage()`);
  клик по самому уведомлению тоже открывает страницу.
- **ntfy по `http://`** — токен уходил открытым текстом; теперь только `https://` (проверка в popup и в `sendNtfy`).
- **Токен бота в истории браузера** — ссылка getUpdates открывала вкладку с токеном в адресе; теперь popup сам делает
  запрос и подставляет Chat ID.
- **Пороги в паузе** приходили устаревшими после снятия паузы — теперь пропущенный в паузе порог помечается отработанным
  (тик бейджа проверяет пороги и в паузе).
- **Два порога с одинаковыми минутами** — «Сохранить» теперь отказывает с подсказкой.
- Не исправимо: пароль прокси и токены лежат в `chrome.storage.local` открытым текстом — у расширений иначе нельзя.

## P2 — мелочи

- ~~**Markdown в Telegram.**~~ ИСПРАВЛЕНО: `sendTelegram()` шлёт простой текст без `parse_mode`.
- **Свой сервер ntfy.** В `host_permissions` только `ntfy.sh`; для другого сервера `fetch` сработает лишь при
  CORS-заголовках. Решение: `optional_host_permissions` + запрос разрешения при сохранении настроек.
- **`onMessage` всегда `return true`** (≈516) — держит канал открытым и для синхронных/неизвестных сообщений.
  Возвращать `true` только в асинхронных ветках.
- **`DEBUG_RESET`** (≈502–514) сбрасывает состояние в памяти, но не `pvzSettings`/`timerState` в storage — после
  перезапуска SW всё вернётся.
- **Период `badge_tick`:** `periodInMinutes: 10/60`; Chrome может ограничивать минимальный период алармов (порядка 30 с)
  — бейдж обновляется не чаще (не проверялось). Секундный таймер в popup рисуется отдельно.
- ~~**Лишнее в манифесте.**~~ ИСПРАВЛЕНО: убраны `activeTab`, `tabs`, `*://*.ozon.ru/*`, `*://*.ozon.com/*`; голос
  ищет вкладки только `turbo-pvz.ozon.ru` (по `host_permissions`). `proxy`/`webRequest*` нужны модулю прокси (п. 2).
- **Версия:** `manifest.json` `version` всё ещё 1.4.0 (после добавления модуля пакетов не менялась) — поднять до 1.5.0
  при следующем релизе и дописать `description`.
- **Мёртвый код:** шаблоны `seller.ozon.ru` в `URL_WHITELIST` (`content.js`) — манифест подключает скрипты только на
  `turbo-pvz.ozon.ru`; обработчики `GET_TIMER_STATUS` и `SET_DEBUG_MODE` в `content.js` нигде не вызываются
  (`npm run check` предупреждает); комментарий в `speech.js` про «все страницы Ozon» устарел.
- **Заморозка вкладок.** В консоли Ozon видны «The page is being frozen» и «Page entered Back-Forward Cache» — фоновые
  вкладки замораживаются, `setInterval` в `content.js` тогда не тикает. Пороги это не ломает (они на `chrome.alarms`
  от абсолютного времени), но только после исправления п. 1.
